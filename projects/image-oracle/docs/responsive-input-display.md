# 按键与屏幕为什么会卡：任务、局部重绘与非阻塞日志

记录日期：2026-09-19。案例来自 ESP32-S3-CAM N16R8、GPIO14 中心按键、240×240 ST7789 屏幕。本案例固件是 `button-counter-usb-nonblocking`，用户已确认持续连按、停顿后再按均跟手。原始测量与烧录过程见[按键启动记录](button-bringup.md)；当前整合程序已复用这些方法，见[第三个程序记录](oracle-bringup.md)。

## 先分清“没记下来”与“没显示出来”

旧程序在同一个循环里完成全部工作：

```text
读取按键 → 更新计数 → 清屏并重画 → 发 USB 日志 → 下一次读取按键
```

只要绘图或日志发送慢，下一轮按键读取就会推迟。如果手指在这段空档中完成一次按下和松开，程序可能从始至终只读到松开，漏掉这次操作。

改成独立采样任务后，按键仍会被记下来；但如果绘图循环被日志卡住，屏幕会停在旧值，恢复时一次跳到最新总数。所以“不丢计数”和“画面跟手”需要分别验证。

| 本次现象 | 定位结果 | 对应技术 |
| --- | --- | --- |
| 快速连按漏计数 | 绘图期间没有读取 GPIO | FreeRTOS 独立采样任务、短临界区共享状态 |
| 能看到整屏从上到下刷新 | 每次都清屏并传输整页像素 | 局部重绘、内存画布 |
| 开始跟手，随后几次合并更新 | USB 发送缓冲满，绘图循环等待日志发送 | 非阻塞 I/O、有界缓冲、允许丢弃诊断日志 |
| 一次机械按压可能出现多个电平边沿 | 触点在接触、释放时抖动 | 基于稳定时间的消抖、按下边沿计数 |

## 任务解耦：按键有自己的执行机会

FreeRTOS 是固件中的实时操作系统，负责在多个任务间调度 CPU。这里创建了一个专门的按键任务：

- `sample_button()` 目标每 1 ms 运行一次，只做 GPIO 读取、消抖和累计次数。
- 按键任务优先级为 2，Arduino 主循环任务优先级为 1；按键任务就绪时可以抢占主循环，运行一小段后休眠，让主循环继续工作。
- 两个任务均使用当前配置的同一个核心。改善来自及时调度；没有将按键与绘图分别分配到两个核心。
- 本次采用周期轮询，没有为按键编写 GPIO 中断服务函数。`vTaskDelayUntil()` 按周期安排唤醒，不是让任务持续占住 CPU 空转。

优先级、抢占和任务固定核心的概念见 [ESP-IDF 5.5.5 FreeRTOS 文档](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/api-reference/system/freertos_idf.html)。实际采样周期会受调度和临界区影响；本次无读取端压力测试的采样最大间隔为 1.172 ms，不能把目标 1 ms 当成永远精确的保证。

两个任务访问同一份计数和按键状态时，用 `portENTER_CRITICAL()`／`portEXIT_CRITICAL()` 保护很短的更新或复制过程，防止读到更新一半的状态。绘图和日志都在临界区外执行。仅使用 `volatile` 不能替代这种同步。

主循环读取最新计数并显示。计数器足以保存本例“按了多少次”的信息；如果将来每次按键分别对应不同动作或需要顺序、时间信息，就需要另行设计事件队列及队列满时的处理，不能只保存一个总数。

```mermaid
flowchart LR
    A[按键采样任务：约每 1 ms] --> B[共享计数：短临界区保护]
    B --> C[主循环读取最新计数]
    C --> D[内存绘图并更新数字区域]
    D --> E[尝试发送 USB 日志]
    E --> F{缓冲够吗？}
    F -->|够| G[入队后继续循环]
    F -->|不够| H[跳过日志并继续循环]
```

## 局部重绘：减少要传输的像素

屏幕中的数字变化了，标题、边框和接线说明没有变化。因此进入页面时画完整页面，之后只更新数字所在的矩形区域。这通常称为局部重绘，或更新脏矩形（dirty rectangle）。

本例屏幕为 RGB565，每像素 2 字节，SPI 保持 8 MHz：

| 更新范围 | 像素数据量 | 只计像素传输的理论下限 |
| --- | --- | --- |
| 整屏 240×240 | 115,200 字节 | 115.2 ms |
| 数字区域 180×24 | 8,640 字节 | 8.64 ms |

理论下限是 `像素数 × 每像素 16 bit ÷ 8,000,000 bit/s`，还没有算绘图、命令、调度等开销。实测局部绘图约 9.6 ms；旧版 `COUNTER` 命令约 152 ms 的测量还包含 USB 往返，两个指标应注明范围。

`GFXcanvas16` 是 RAM 中的一小块像素画布：先把黑背景和新数字完整画在内存里，再通过 `drawRGBBitmap()` 写到屏幕对应位置。屏幕不会先经历一次整屏清空，旧数字的残留也会被覆盖。这属于离屏绘制，不等于全屏双缓冲交换，也没有启用扫描同步；仍然需要通过 SPI 传输这些像素。

画布与减少闪烁的机制见 [Adafruit GFX 文档](https://learn.adafruit.com/adafruit-gfx-graphics-library/minimizing-redraw-flicker)。代码入口是 [draw_counter_value() 所在源码](../firmware/display_serial/display_serial.ino)。

## 非阻塞日志：下游慢时，不让交互一起等

`Serial.printf()` 看起来只有一行，但里面可能执行格式化、申请发送缓冲和等待缓冲空位。USB 插在电脑上，不代表电脑上有程序正在读取这些字节。

本例中，日志最初能放进缓冲，所以前几次很流畅。主机停止取数据、缓冲填满后，写入函数开始等待；绘图循环停在该函数内，就无法及时显示新的计数。这种“接收方来不及接收，压力传回发送方”的现象叫背压（backpressure）。

固定版本 Arduino-ESP32 3.3.11 的 Hardware CDC 默认发送等待为每轮 100 ms，连续失败上限 20 次。实际复现单次 USB 输出等待 1,999.978 ms。版本实现见 [HWCDC.cpp](https://github.com/espressif/arduino-esp32/blob/3.3.11/cores/esp32/HWCDC.cpp)。

修复采用以下策略：

1. `Serial.setTxTimeoutMs(0)`：发送不等待缓冲空位。
2. `Serial.availableForWrite()`：先确认能放下整条消息，避免明知空间不足仍去写。
3. 放不下时跳过该消息，增加 `usb_dropped`，继续交互。按键总数保存在另一份状态中，不随日志丢失。
4. TX 缓冲设为 1,024 字节，以容纳一条完整状态回复。这个大小解决单条消息容量；零等待与跳过策略解决持续堵塞。

关键代码可概括为以下片段；API 对应本项目的 ESP32 Hardware CDC，完整边界检查见 [send_usb()](../firmware/display_serial/display_serial.ino)：

```cpp
// Configure once during setup.
Serial.setTxTimeoutMs(0);

// Each diagnostic message may be skipped if the host is not consuming it.
if (Serial.availableForWrite() >= length) {
  Serial.write(data, length);
} else {
  ++usb_messages_dropped;
}
```

缓冲的作用是吸收短暂速度差。接收方持续不读取时，再大的有限缓冲最终也会满；因此“把缓冲加大”只能推迟卡顿。单纯把日志搬进另一任务也需要有界队列和满队列策略，否则只是把堵塞点换了位置。

这里可跳过的是诊断信息。当前实验协议的状态和命令回复也采用尽力发送，恢复读取后可重新查询；写入缓冲成功不表示电脑已经接收。重要业务命令、照片文件或必须逐条保留的事件需要明确的确认、重试、队列或错误反馈，不能直接复用丢日志策略。

## 消抖：确认一次真实按下

机械触点按下和松开时可能短暂反复通断。`button_debouncer.h` 每次看到电平变化就重新计时，连续稳定 10 ms 后才承认新状态；只有状态变为“按下”时累计一次。

因此长时间保持按下不会不断加一，必须先稳定松开再稳定按下。当前通过时间判断消抖，没有在采样任务中用阻塞式 `delay(10)` 等待稳定。阈值从原来的 30 ms 调整到 10 ms；更小的值有利于快速响应，但需要结合真实触点抖动验证，不能无限减小。

纯逻辑测试覆盖抖动、长按、100 次快速按压、毫秒计时回绕和上电时已按住。用户已验证持续连按的跟手程度；固定次数和长按专项验收的历史状态见实验记录。

## 如何证明修复有效

分别给 GPIO 采样、绘图、USB 输出和主循环间隔计时，保留峰值，而不是只看平均帧率。偶发的一次 2 秒等待可能被大量快速调用的平均值掩盖。

同一块板子的无读取端对照测试中：

| 指标 | 保留阻塞输出 | 修复后 |
| --- | --- | --- |
| 单次 USB 输出最大耗时 | 1,999.978 ms | 0.212 ms |
| 数字局部绘图最大耗时 | 9.574 ms | 9.580 ms |
| 按键采样最大间隔 | 1.146 ms | 1.172 ms |

绘图时间几乎不变、USB 等待消失，再结合用户复测“始终跟手，问题解决”，才确认了第二个卡点。相应诊断字段为 `usb_write_max_us`、`counter_draw_max_us`、`sample_gap_max_us` 与 `loop_gap_max_us`。

从仓库根目录查询指标：

```sh
uv run --offline projects/image-oracle/scripts/display.py --port /dev/cu.usbmodem1101 STATUS
```

需要复现无读取端条件时，先正常复位以清空历史峰值，再执行下列测试。它会暂时切换测试页、关闭串口读取端 20 秒，最后恢复计数页；不要同时开其他串口客户端。

```sh
uv run --offline projects/image-oracle/tests/usb_backpressure.py --port /dev/cu.usbmodem1101
```

完整编译、烧录及消抖测试命令见[固件工程说明](../firmware/display_serial/README.md)。

## 后续项目怎么沿用

- 先确定输入允许多长时间不采样，再决定采用短循环、状态机、任务或中断。当前 1 ms 周期、10 ms 消抖与任务优先级是本例参数，不是所有硬件的统一标准。
- 时间敏感的采集与慢速绘图、网络、文件或日志分开安排；共享状态保护要短，不在锁内执行慢操作。
- 界面尽量只传变化部分。累计次数可以显示最新总数；必须逐条执行的操作则保留事件及顺序。
- 日志使用有界、可跳过的输出。为业务数据单独确定满队列、超时和恢复策略。
- 分段测量峰值，测试正常读取、停止读取、持续输入和恢复后的表现。读取日志本身可能排空缓冲、改变故障条件，需专门做无读取端测试。

这些方法与本例数据一起保留；复用原则，重新验证具体设备和时间预算。
